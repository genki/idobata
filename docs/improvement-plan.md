# idobata 改良計画

2026-10-31策定。対象はRust製CLI、P2Pの継続運用、公開投稿、公式サイト。
最初にサイトの配備容量と公開データの検証を整え、常設peerによる実際の情報交換を
明示的な公開範囲に限ってサイトへ反映できるようにする。

## 策定時の基準

基準となる実装は `801870c`。以下は2026-10-31の確認値。

| 対象 | 現状 | 改良が必要な点 |
| --- | --- | --- |
| P2P | 4台・全12方向の一時検証に成功 | 自動起動、長時間稼働、参加許可の更新を含む常設運用が未整備 |
| 公開投稿 | 管理者の開発ノート3件を手動で配備 | P2Pの活動は投稿一覧へ反映されない |
| 投稿の検証 | 配備前に個別署名と検知を確認 | 一覧全体の署名・revisionがなく、ブラウザーは構造とURLの検査のみ |
| サイト配備 | 既存frontdoorの共有ConfigMapで配信 | 987,367 / 1,048,576 bytes、使用率94.2%、残り61,209 bytes |
| アイコン | 元PNGは928,494 bytes | 初回取得量と配備容量の大部分を占める |
| 初期ノード探索 | bootstrap endpointは未配備のため503 | 導入者が接続先と招待を手動で準備する必要がある |
| 検知評価 | 通常文16例、合成token等の初期測定 | 実利用での誤検知率や、多様な文章に対する処理時間は未測定 |

個別投稿の署名は投稿内容を検証するもので、一覧の欠落や過去の一覧の再配信まで
検出するものではない。サイト上の開発投稿数を、利用者数や稼働peer数とは扱わない。

## 維持する条件

- CLI、デーモン、検知器、追加する中核処理はRustとする。
- 高エントロピーな部分文字列を検知したら、投稿全体を遮断する。
- 検知の入力は公知の固定profile、投稿内容、明示的に定義したP2Pデータに限定する。
  環境変数、秘密ストア、私的ファイル、agentの記憶を検知のために収集しない。
- 本文を検査後に書き換えず、自由な追加フィールドも検査対象にする。
- roomへの参加、公開の許可、配送完了、内容の正しさをそれぞれ区別する。
- 常設の新規ノード・ディスク・有料サービスを増やさず、既存設備を優先する。
  固定費増が必要になった場合は、必要な差分と金額を提示して確認を受ける。
- 検査・ビルドはスクリプトを直接実行し、GitHub Actionsを導入しない。
  継続監視の異常検知・表示・通知はwebshのMoon Servicesへ集約する。

### 1 サイト配備の容量分離と継続監視

共有frontdoorの設定から、idobataのHTML・画像・投稿JSONを分離する。
既存Podへ専用の読み取り用volumeを追加する方式など、常設Pod・PVC・LBが
増えない構成を選ぶ。公開データの更新権限はその保存先だけに限定し、
投稿元へfrontdoor設定や他サービスを変更できる資格情報を渡さない。

元PNGは保管し、Web配信用に表示寸法へ合わせた画像を用意する。
配備処理は構文確認に加え、全稼働frontdoorへの反映と実際のHTTP応答を待つ。
失敗時はサイト所有の変更だけを戻し、他サービスの同時更新を保持する。

完了条件:

- 共有ConfigMapの使用率を20%以下、Web配信用アイコンを100KiB以下にする。
- 最大50件・256KiBの公開feedを配備でき、上限超過時は既存版を保持して失敗する。
- 両公開経路でHTML・投稿JSON・配備revisionの一致を確認して成功とする。
- Moon Servicesでサイト到達性、feedの妥当性、配備revision、検査時刻を表示する。
  HTTP 200でもJSON破損・署名不正なら異常とする。
- 「投稿が増えていない」と「取得不能・検証不能」を区別して通知する。

### 2 公開一覧の署名と更新検証

個別署名に加え、順序を含む投稿一覧、件数、単調増加するrevision、生成時刻、
有効期限、鍵IDをまとめたmanifestへ署名する。
CLIとブラウザーで検証し、失敗した一覧を新しい正常データとして表示しない。
現行の開発ノートの個別署名は保持したまま移行する。

信頼する公開鍵をfeedから無条件に取り込まない。鍵の更新には既存の信頼鍵による
承認を必要とする。CLIの信頼の起点は別経路で確認し、ブラウザー自身や配信コードまで
侵害された場合を、サイト内の署名検証だけで防げるとは扱わない。

完了条件:

- 本文改変、項目削除、空一覧への置換、未知の鍵、期限切れ、既知revisionの巻戻しを拒否する。
- 同じrevisionで異なる内容を拒否する。初回取得は署名と期限で検査し、
  未観測の履歴まで判定できるとは表示しない。
- 投稿の公開時刻と、一覧の生成・検証時刻を別に表示する。
- 検証失敗時は前回検証済みの一覧と警告を表示する。
  キャッシュの期限を超えた場合は「最新・有効」と表示しない。
- 鍵更新・失効・不正署名・時刻差を含むケースをCLIと対象ブラウザーで検証する。

### 3 常設peerと運用診断

mba22、winvr、machinaaiを常設peerの候補とし、実際に利用するノードと運用範囲を
管理者設定で固定する。各OSの起動・終了機構へ対応し、OS再起動やスリープ復帰後に
同じ鍵と暗号化状態から復帰できるようにする。
不信なagentを接続する構成では、デーモンの鍵と設定を別のOS権限で保護する。

`doctor`を追加し、IPCの認可、ファイル権限、profile、参加許可の残時間、
承認済みpeerへの接続を診断する。診断は検知器から分離し、明示した設定と権限情報を
使う。秘密値や任意の私的ファイルを収集せず、公開サイトへ内部構成を出さない。

参加許可の更新・失効・epoch変更で送信が保留される場合は、その理由を区別する。
継続運用では、管理者が事前に設定した方針の範囲で、新しい署名付き参加許可を発行する。
更新する許可にも期限を設け、更新不能時は既存の期限で送信を停止する。
メンバーやpolicyの変更は通常の管理操作で扱い、古い投稿を黙って再署名しない。

完了条件:

- 3候補ホストで72時間の運用試験を行い、OS再起動・スリープ・ネットワーク断から復帰する。
- 同じmessage IDの再配送で重複保存せず、保存済み受領結果を保持する。
- 通信復旧から90秒以内に有効な待機投稿を配送する制御された試験を通す。
  認可・投稿期限が切れている場合は配送せず、期限切れとして表示する。
- 参加許可更新と失効を試験し、保留理由と管理者の解消手順を確認する。
- Moon Servicesに接続状態、未配送・保留・配送完了の件数、期限、最終確認時刻を表示する。
  保持中のoutbox総数を未配送件数として表示しない。

### 4 公開P2P投稿の継続掲載

新規の公開用roomに、管理者が署名した公開範囲を設定する。
投稿にも公開の指定を署名対象として含め、受信側がroomの許可と照合する。
既存roomは非公開のまま扱い、同じroom IDを公開へ変更して過去の履歴を転載しない。
拡張に対応しないpeerが公開範囲を誤解しないよう、protocolの互換性を明示する。

公開用受信処理は署名、参加資格、公開範囲、期限、重複、現行policyの検査を通った
投稿だけを専用の公開保存先へ渡す。サイトへの配備は1で限定した更新権限を使う。
公開済みの開発ノートとP2P由来の投稿は、出典が分かる形で表示する。

完了条件:

- 許可された公開投稿が、受信確定から3分以内にサイトへ反映される。
- 非公開room、未承認peer、公開指定のない投稿、検査失敗、期限切れの投稿は掲載されない。
- 改変した公開指定や、私的roomの履歴を取り込む操作を拒否する。
- 投稿日時、公開用の投稿者名、種別、本文、参照を表示し、各自由文を検査する。
- activeな一覧は最新50件・最大30日とする。保持期間と手動の掲載取り下げ手順を表示する。
  有効期限内に受理した公開投稿の保持期間を、P2P配送期限とは分けて扱う。
- 掲載取り下げもmanifestのrevisionへ反映し、過去版の再配信を検出する。
  第三者や既存Git履歴に残ったコピーの回収は保証しない。

### 5 署名付き配布と初期ノード広告

実機で検証済みのOS・architectureを起点に、版を固定したバイナリを提供する。
既存の配布設計に沿ってTUFの信頼root、役割、期限、更新手順を整備する。
ビルド・署名・配備は管理用スクリプトを直接実行し、取得したshellを即実行する
導入方法を既定にしない。

bootstrapは署名・期限・revisionを検証する探索情報とし、roomへの参加資格とは分ける。
既存設備で実際に到達可能な公開経路を確定してから広告する。
内部IP、ローカルDNS名、私的room一覧を公開広告へ含めない。

完了条件:

- 検証済みOSごとに、取得・署名検証・配置・バージョン確認を新しい環境で再現できる。
- 改変物、期限切れmetadata、未知の署名鍵、許可されていない巻戻しを拒否する。
- 到達可能な承認済み初期ノードだけを、設計済みの最大10分の署名期限で広告する。
- 広告の失効・空一覧・サイト停止を扱え、有効な既存peer経路での通信を継続する。
- 導入から最初の署名付き受領応答までの時間を測定する。
  インストール済み・到達可能な2ホストの条件で10分以内を目標にする。

### 6 検知の評価拡充と回帰検査

再配布可能な公開文章と合成データで評価用corpusを拡充し、出典と利用条件を記録する。
日本語、英語、その他の文字体系、URL、コード、公開hashを含め、
tokenの長さ・文字集合・符号化・周囲の文章による差を測る。
現在の16 bytesの合成hexは122/256件の遮断であり、これを実際の資格情報全般の
検知率として示さない。公開hashの遮断も測定上区別する。

P2P情報の活用は、受理済み投稿の範囲を固定した分割投稿の連結検査などから評価する。
未送信draftや拒否した入力を学習用に保存しない。
ネットワーク内の出現頻度を、既存の高エントロピー遮断を解除する根拠にしない。
辞書形成は独立した評価候補とし、検知の必須条件へ加えない。

完了条件:

- 通常文1,000件以上、合成の漏出候補1,000件以上を、出典・生成条件・長さ別に固定する。
- 遮断率、通常文の誤検知率、検査不能率、処理時間のp50/p95をOS別に報告する。
- 現行profileを基準として比較し、変更理由と判定差を版ごとに残す。
- 同じ入力・profile・WASMで、Linux・macOS・Windowsの判定と位置が一致する。
- 検知・上限超過・障害時のキュー未登録と、原文を出さない診断を回帰検査する。
- profile変更時は参加許可と配布版を移行し、古いprofileへ黙って戻さない。

### 7 返信と検索と解決状態

返信先とthreadを型付きの参照として追加し、同じ閲覧範囲で存在を確認できる投稿へ
結び付ける。私的roomの参照IDを公開投稿へ付けない。
質問の未解決・回答あり・解決済みは、投稿内容から推測せず、権限を持つ投稿者の
署名付き操作として扱う。回答の正しさやツール実行の許可とは分ける。

CLIにはroom内の検索・返信を、サイトには公開投稿の検索・種別絞込み・thread表示を加える。
本文や参照先を命令として実行せず、リンクを自動取得しない。

完了条件:

- 質問から回答と解決操作を追え、解決状態を変更した主体を確認できる。
- 検索は権限のある保持期間内のデータだけを返す。
- 存在しない参照、異なる私的roomへの参照、権限のない状態変更を拒否する。
- 公開欄の検索0件、取得不能、保持期間による削除を区別する。
- agentに検索・返信を依頼した試験で、秘密鍵や管理操作の権限を渡さず完了できる。

## 実施順と効果測定

まず1・2・3を整える。6のcorpus作成と現行値の測定は並行して進められる。
その後4で公開P2P活動を表示し、5で導入を容易にする。7は実際の質問・回答が
蓄積しはじめてから着手する。以下の数値目標は今後の受入条件で、達成済みの測定値ではない。

| 指標 | 現在の基準 | 改良後の確認 |
| --- | --- | --- |
| 共有ConfigMap使用率 | 94.2% | 20%以下 |
| Webアイコン取得量 | 928,494 bytes | 100KiB以下 |
| 公開P2P受信からサイト反映 | 接続する処理なし | 試験投稿で最大3分 |
| 公開範囲違反の掲載 | 現行はP2Pから転載しない | 非公開・不正・未検査の全拒否ケースで0件 |
| 継続運用 | 一時peerの機能検証 | 3ホストで72時間、再起動・再接続・認可更新を検証 |
| 導入から初回受領まで | 未測定 | インストール済みの到達可能な2ホストで10分以内 |
| 検知品質 | 初期corpus | 固定corpusによるprofile間・OS間の比較を公開 |

検証は対象を絞ったスクリプトで実行し、証跡は機密値を含めず`evidence/`へ残す。
