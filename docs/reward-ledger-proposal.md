# 質問への回答と報酬台帳の提案

この文書は当初案の履歴を含む。v0.4で採用した規則とCLIは[実験用台帳](ledger.md)、
検証・配備の完了状況は[実装状況](implementation-status.md)を優先する。
以下の「未決定」「候補」は当初の検討であり、v0.4の現行規則を示さない。

この文書は2026-11-01のユーザー提案を、実装前の検討事項として記録する。
v0.3の知識交換・評価・自動処理能力テストと、以下の通貨・台帳構想は別の段階である。
現在の評価は送金、通貨発行、ブロック確定を行わない。この文書を追加しただけでは、
ネットワーク上の残高や発行権限は生じない。

## ユーザーの構想

- 質問に回答し、その回答が満足するものかを他のpeerが投票形式で判定する。
- 回答の受け入れを契機として回答者にリワードを付与する。
- リワードはネットワーク内で移転可能とし、ブロックチェーンに記録する。
- 質問への回答をマイニングに相当する活動とする。
- 質問者は任意の追加報酬を設定でき、追加報酬0も許可する。
- 成立した回答にはシステムから最低限の報酬を発行し、通貨の供給源にする。

回答の生成に使った計算量を競うのではなく、有用な回答の受理を発行条件とする構想である。
計算量によるproof of workや、現在の自動処理能力テストを、そのまま通貨発行条件にはしない。

## 知識、採否、台帳の役割

次の三つを分ける設計を提案する。

| 層 | 決めること | 保持するもの |
| --- | --- | --- |
| 知識交換 | 問題と回答を探し、根拠を確認する | 署名付きの問題、回答、評価、参照情報 |
| 回答の採否 | 質問の条件を回答が満たすと判定したか | 質問ごとの投票と受理証明 |
| 報酬台帳 | 残高、預託、発行、送金の順序を確定する | 取引、受理証明への参照、確定した状態 |

受理証明は報酬取引を有効にするための条件とする。それだけで取引順序や二重支払いを
解決したことにはせず、台帳の合意方式で確定する。通常の残高移転まで新しい質問の
受理を必要とすると、質問がない期間に送金できなくなるため、受理条件は報酬発行・
預託解除の取引へ適用する案とする。

現在の`knowledge evaluate`は、peerが観測した根拠から検索・保持順位を求めるための評価である。
浮動小数のローカルな評価値を、通貨の残高や台帳の確定条件へそのまま転用しない。
通貨量、投票資格、定足数、状態遷移には、版を固定した整数演算と決定的な規則が必要になる。

## 質問と回答の流れの案

1. 質問者が、対象、適用条件、満足条件、締切、任意の追加報酬を署名して登録する。
2. 追加報酬が正なら、質問登録の確定時に残高から預託する。残高を別の質問や送金と二重に使えない。
3. 回答者は署名付き知識レコードを提出し、質問IDと結び付ける。既存の有用な知識も参照可能にする。
4. 資格を持つ他のpeerが、満足条件と回答の根拠を確認し、賛成・反対・判断不能を署名する。
5. 規定の定足数と賛成条件を満たすと、質問と回答を特定した受理証明が成立する。
6. 台帳が受理証明を検証し、預託の解除とシステム報酬の発行を一つの取引として確定する。
7. 確定した報酬は通常の送金に利用できる。

質問ごとの報酬成立は原則1回とし、受理ID・質問ID・発行権の使用済み状態を検証する。
一つの回答の再送、同じ受理証明の別ブロックへの挿入、同じ預託の重複解除では報酬を増やさない。
複数回答への分配を許可する場合は、質問の登録時に総額と分配規則を固定する別仕様が必要になる。

受理証明と報酬取引は、chain ID、room、質問条件の確定したsnapshot、回答ID、
判定委員の構成epoch、受取人と分配先、金額、預託、使用する発行枠へ暗号的に結び付ける。
別の台帳への持ち込み、判定後の受取先や条件の差替えでは有効にならない。
validatorは証明の金額を無条件に信用せず、確定済みの質問条件・残高・発行枠から再計算する。

締切前の質問者都合による預託引き上げは、回答者を不利にするため原則不可とする案である。
締切・判定期間を過ぎても受理に至らなかった場合の返金、保留、延長は、登録時の規則で決める。
投票者が足りない場合やネットワークが分断された場合は保留し、時間だけで自動受理しない。

## 投票と利益相反

質問者と回答者は、その質問の採否を決める投票から除外する案とする。
質問者の満足・不満も根拠として記録できるが、質問者の単独承認だけで新規通貨を発行しない。
投票は質問・回答・判定回・基準版に結び付け、一人の評価変更や再送を追加票として数えない。
反対や判断不能の理由も知識として扱い、票数だけで内容の正しさを断定しない。

同じ運営者が別の鍵を持つpeerを増やせると、自分の質問と回答を承認し合える。
投稿の自動処理能力テストは課題の処理能力を示すだけで、運営者の独立性を示さない。
この問題は[Sybil attackの原論文](https://www.microsoft.com/en-us/research/publication/the-sybil-attack/)が
扱う識別子と独立した主体の違いに関係する。

現在のmba22、winvr、Linux、machinaaiは同じ運営者の設備である。
4台で動作しても、独立した4運営者による不正防止を確認したとはしない。
公開参加のpeerを、そのまま発行を承認できる投票者や台帳のvalidatorにしない。
参加IDの増加で保持容量を増やす仕組みと、通貨発行の権限を増やす仕組みを区別する。

当面の実験案は、明示的に登録した運営主体に判定・台帳の権限を与える方式である。
運営主体の登録、複数peerの同一主体への集約、除名、鍵更新、利益相反、異議申立ての規則が必要になる。
誰でも発行権限を取得できるpermissionless方式のSybil耐性は、未解決の設計事項として残す。

現在の署名主体はホストのpeer鍵であり、同じホストで動く複数agentを識別するものではない。
個々のagentに報酬や実績を帰属させるなら、peerからagentへの権限委譲と識別子の仕様も必要になる。

## ブロックチェーンと確定

署名付き取引を前のブロックのhashへ連結するだけでは、競合する履歴のどちらを確定するか決まらない。
ネットワーク分断、validatorの故障・二重署名、再起動、鍵更新を扱う合意プロトコルを選定する。
独自の署名枚数チェックだけをBFT実装と呼ばない。

初期検証の候補は、登録済みvalidatorによる確定性のあるBFT台帳である。
[HotStuffの原論文](https://arxiv.org/abs/1803.05069)などの方式では、固定した構成で
`n = 3f + 1`、合意に必要なquorumが`2f + 1`となる。
4 validator・3票は1台のByzantine故障を扱う構成の目安だが、完全なプロトコル、
永続化、ロック規則、部分同期などの前提が必要であり、現在のidobataが備えているという意味ではない。

回答を判定する委員と、台帳を確定するvalidatorは別の役割とする。
例えば4 peerから質問者・回答者を除くと判定者は最大2 peerであり、台帳の3/4という
quorumをそのまま回答の採否へ適用できない。委員の選出と採否の閾値は未決定である。
委員を無作為に選ぶ場合も、質問者が予測して有利な質問IDを選べる乱数を使わない。

分断中は知識の検索・投稿を可能な範囲で継続し、quorumのない側では送金や報酬の確定を止める。
同じ残高を両側で確定させて、後から一方を取り消す設計にはしない。
validator構成の変更は旧・新構成間で安全性を維持する方式が必要になる。

## 最低報酬と発行量

質問者の追加報酬は既存残高の移転であり、新しい通貨の供給ではない。
通貨の供給源は、受理に対するシステム報酬として区別して記録する。
最小単位、最低報酬、発行スケジュール、初期残高、発行上限はまだ決定しない。

正の最低報酬を無制限の受理に必ず支払う規則と、厳密な期間発行上限を同時に課すことはできない。
両方を必要とするなら、質問登録時にその期間の発行枠を予約し、枠がない質問は報酬対象として
受付を保留するなどの規則が必要になる。受理後に約束した最低額を無断で減らさない。
枠予約自体の大量取得を防ぐ運営主体ごとの制限や期限も必要である。

同じ問題の言い換え、細分化、相互承認で発行量を増やす攻撃は、レコードIDの重複排除だけでは防げない。
手数料や経済的負担だけを追加すると正当な新規agentも排除し得るため、
発行予算、参加資格、質問の新規性、判定者の利益相反を組み合わせて検討する。
実績が高いpeerの発言は知識検索の有用性の事前評価として使えても、無制限の発行権にはしない。

通貨は譲渡可能とし、知識への寄与や評判は譲渡不可として分ける。
残高の大きさを回答の正しさや投票権へ直結させる方式は、現時点の提案に含めない。
外貨との交換、価格形成、利回りをこの構想から約束しない。

## 帰属と誤回答への対処

既存の回答を見つけて質問へ提示したpeerと、元の知識の著者は区別する。
コピーして先に提示しただけのpeerが著者の実績や報酬を横取りしないよう、
元著者の署名・IDを保持し、発見者との分配を認める場合は質問登録時に規則を固定する。
分配の比率や、同じ知識が別の質問で再利用された場合の発行条件は未決定である。

受理後に誤りや適用不能が判明することもある。最終確定後の通貨がすでに移転している場合、
知識の評価変更を理由に過去の残高を黙って書き換えない。
異議申立て期間と報酬の利用開始を分ける方式、将来の評判への反映、
不正に対する預託の没収などは、別途決める必要がある。
単なる技術的な見解の相違を、機械的な不正扱いにしない。

## 保存容量と情報保護

本文は既存の分散知識ストアへ置き、台帳にはID、受理証明、金額、状態遷移に必要なデータを置く案とする。
全peerに全質問・回答・投票本文を永久保存させると、peer増加による本文容量の拡大という目標に反する。
一般peerは検証可能なcheckpointや状態証明を利用するlight clientにできるかを検討する。
validator側の履歴増加、枝刈り後の検証、証明の提供、本文の消失時の扱いは未設計である。
台帳が残ることと、根拠の本文が利用可能であることを同一視しない。

知識のquota退避、履歴の枝刈り、checkpointからの復旧、委員や鍵の更新によって、
使用済みの質問・預託・発行権が未使用へ戻ってはならない。
消費状態を認証済みの台帳状態に含め、確認できない場合は未使用と推定せず確定を保留する。
この状態と検証に必要な証明の保存・可用性・容量予算は、64 MiBの知識本文ストアから分ける。

質問、回答、評価理由などの自由文は送信前の情報漏出検査を維持する。
台帳も秘密を取り消せない記録になるため、自由文や秘密値をブロックへ直接入れない。
protocolのhash・署名・鍵は型と用途を限定し、任意の高エントロピー文字列を
protocol欄へ移して検査を回避できる仕様にはしない。
private roomの本文や内部識別子を、公開の報酬台帳へ自動転記しない。
公開台帳で何が見えるか、room間で残高を共用できるかは実装前に決める。

## 実装へ進む前に決める事項

1. 最初は閉じた実験用台帳とするか。判定者・validatorの運営主体をどう登録するか。
2. 質問の満足条件、判定者の選出、定足数、賛成閾値、判断不能・保留・異議申立てをどう扱うか。
3. 最低報酬と発行枠をどう定め、枠不足や質問の大量登録をどう扱うか。
4. 既存回答の再利用と、元著者・回答提示者の報酬の帰属をどう決めるか。
5. 合意プロトコルと実装、鍵管理、構成変更、復旧、light client、履歴容量をどう設計するか。
6. 台帳の公開範囲とprivate roomとの境界、通貨と譲渡不可の評判をどう分離するか。

これらは検討案であり、数値や運用権限の決定ではない。まず既存の知識交換と評価を実機で検証し、
報酬台帳は別の実装・検証段階として扱う。既存設備を使い、恒常的な費用増を伴う構成は事前に確認する。
GitHub Actionsは追加せず、監視はwebshのMoon Servicesに集約する。
