## 初期の台帳規則

CLIと採用規則の詳細は[実験用台帳](ledger.md)を参照する。

- 本文・根拠は分散知識ストア、台帳には検証済みレコード参照と取引・採否・残高を置く。任意の自由文を暗号的ID欄へ移して検査を迂回させない。
- 単一の招待制roomを対象とする実験用genesisへ、authority、参加者とoperator、パラメータを署名固定する。外部価格や換金価値は設定しない。
- 最小整数単位で最低報酬1、100 blockのepochごとに発行枠32を初期値とする。質問時に枠を予約し、受理後は一度だけ発行する。
- 追加報酬0、質問手数料0、初期配分0を既定とし、残高0でも質問を登録できる。正の追加報酬だけ既存残高から預託する。
- 手数料・初期配分の別設定はgenesisで明示する。試験用初期配分はoperator合計100単位以内。既存設備へ残高を暗黙に付けない。
- operator当たりepoch内8試行・同時4予約、締切は同epoch内5〜50 blockを初期値とする。枠不足・quorum不足は保留する。
- 質問者・回答者・受益者と同じoperatorを採否の外部支持から除き、3独立operator・信用3000以上・正の支持が負を上回ることを要求する。
- 原著者へ報酬を付け、発見者への分配は初期規則で行わない。同じ質問の元レコードから繰返し発行できないよう、使用済み状態をcheckpointへ含める。
- 悪性operator最大2組を扱う合意構成は、独立7 validator・5票の確定を基準とする。4 validator・3票の故障試験はf=1の別試験と明記する。
- 現在のLinux・mba22・winvr・machinaaiは1運営主体であり、独立quorum未達として保留する。試験用の7主体を実運営者7者と偽装しない。
- validator構成は固定から始め、未対応の構成変更を安全な自動移行と表示しない。署名前の永続化失敗は署名を返さず停止する。

## 公開feedの境界

手動の管理者ノートとP2Pからの自動掲載を分ける。自動掲載はlegacy通知と長期知識を合わせて確認済みを優先し、
未確認は最大2件・operator当たり1件とする。legacy経路や古いcacheで枠を増やさない。
部分取得だけで過去の正常情報を消さず、取得範囲・検証時刻・未確認を正確に表示する。
大きい本文を解答の条件が欠けた状態で掲載せず、省略と全文取得方法を明示する。
元peer ID、証明書、内部接続先、非公開本文、検索語を公開JSONへ混ぜない。

## 受入検証

新機能の単体検証に加えて、独立したプロセスによる受理→発行→送金、利益相反・供給枠・偽造・再送の拒否、
二重提案・二重投票、2敵対主体、分断、再起動、disk失敗、checkpoint復旧・履歴圧縮を検証する。
新しいCLI・サービスは既存UID/SID、鍵と保存データを保持して4台で確認する。
既存公開物・TUF rootを変更せず、新版の配布署名・取得・公開サイトとMoon Servicesを照合する。
GitHub Actionsと新しい有料常設設備は導入しない。

P2P辞書形成は、当初から検討候補であり高エントロピー遮断の必須条件ではない。
検知器は現行の公知profileと入力による判定を維持し、辞書があることを理由に遮断を解除しない。

合意の参照資料: [Tendermintの原論文](https://arxiv.org/abs/1807.04938)、
[署名とlockの仕様](https://docs.tendermint.com/master/spec/consensus/signing.html)。
参照仕様の名前だけで実装・安全性が確認できたとはしない。
