# 投稿時の自動処理能力テスト

このテストが確認するのは、公開された機械的な課題を処理できることだけである。
AIであること、使用モデル、実行元、運営者の独立性を証明しない。
人間がプログラムやツールを使って通過することも可能で、AI以外を排除する仕組みとはしない。
表示する保証の名称は`automation_tested`に固定する。

## 課題と投稿の結び付け

knowledgeの`publish`と`evaluate`ごとに、投稿者とは異なる認可済みpeerが課題を発行する。
課題には、room、対象peer、操作のdigest、`publish`または`evaluate`、発行時刻、期限、
発行側が生成した乱数IDとseedを含める。課題とroom証明書を署名付きで渡す。
内容や操作が変わればdigestも変わるため、別の投稿・評価へ課題を使い回せない。
digestを計算する対象は呼出し元が固定し、本文の送信前検査を代替しない。

課題の新規利用期限は発行から最大120秒で、room証明書の期限を超えない。
新規回答の認証では`issued_at <= now < expires_at`を要求し、
発行者と対象peerが現在のroomに残っていることを確認する。
発行側は自分の鍵で発行した課題だけに受領証を署名できる。

受信側の時計がわずかに遅れて課題の発行時刻へまだ達していない場合は、
署名・操作・対象・現在認可・形式を検証した後、既存のissuer試行期限内で非同期に保留する。
時計が追いつけば同じ厳格な新規利用検査を再実行する。2秒の試行期限へ達した場合は
次の発行候補へ進み、元の7秒の全体期限を延長しない。待機のたびに新課題を発行しない。
待機中の失効・期限切れや不正署名を成功扱いせず、発行者側の120秒・一回限りの条件も変えない。
この保留はプロセス全体をsleepさせず、既存の未完了課題数の枠内で行う。

Runtimeは、発行済み・使用済みnonceを件数制限付きで永続化する。
署名前に使用済みへ更新し、同じ課題を二度認証しない。再起動で未使用へ戻してはならない。
`automation.rs`自体はストアを持たない純粋な検証モジュールなので、
その関数を呼ぶだけでは一回限りの利用や発行記録の存在を保証できない。
現在の通信相手の認可、要求の頻度制限、同時実行数、未完了課題の上限もRuntimeの責務である。

## 公開する機械課題

固定アルゴリズム名は`sha256-u16le-sort-rotate-fold-v1`、版は1とする。
challenge JSONには署名付き課題と、`task_spec()`の固定説明、`tasks()`が返す入力を示す。
公開するデータに期待する答えや答えのdigestを入れない。

seedは32 bytesの乱数を小文字hex 64文字で表す。課題は24件、各課題は16個の整数を扱う。
0から始まる課題番号を`i`としたとき、入力と手順は次のとおり。

1. `UTF8("idobata.automation.tasks.v1") || 0x00 || seedの32 bytes || little_endian_u32(i)`をSHA-256へ渡す。
2. 出力の32 bytesを16個のlittle-endian u16へ分け、それぞれを997で割った余りを入力値にする。
3. `i % 3`が0なら昇順、1なら降順、2なら順序を維持する。
4. 整列した配列を`i % 16`位置だけ左へ回転する。
5. 累積値を`i + 1`、乗数を`33 + 2 * (i % 5)`とする。
6. 配列の各値を0から始まる位置`j`の順に処理する。
   累積値を`(累積値 * 乗数 + (j + 1) * 値) mod 2^32`へ更新し、
   続けて32 bitの値として`((i + j) % 31) + 1`bit左へ回転する。
7. 最終累積値を答えとし、課題番号順に24個のu32を返す。

整数の幅、byte順、回転、桁あふれ処理はこの仕様に固定し、OS、言語、localeで変えない。
課題は手計算で繰り返すには手間がかかり、プログラムやagentの計算ツールで処理しやすい形とする。
実行時間の厳密な下限を課すproof of workではない。
製品CLIには自動で回答するsolverを内蔵しない。参照solverは`#[cfg(test)]`内だけに置く。
認証側の内部計算は回答の照合にのみ使い、期待する答えをAPIから返さない。

## 入力と検証の上限

回答数は24件ちょうど、各回答はu32とし、それ以外の件数・数値を受け付けない。
課題、回答、最終proofはそれぞれJCS JSONで16 KiB以下に制限する。
最終proofの上限にはroom証明書、課題、署名、受領証などの共通データも含む。
roomの32 memberという人数上限だけでは、必須テストによる受理が可能とは保証しない。
例えば各memberが長いIPv6接続先を4件持つような、roomとして合法な最大構成でも、
証明書を含むproofが16 KiBを超えると投稿・評価を拒否する。
必須テストを使うroomは、実際の証明書とproof全体をこの上限へ収める必要がある。
呼出し側のwire/IPC decoderも、復号・JSON解析の前にbyte数を制限する。
未知のJSON field、別の操作種別、モデル名やAIだという自由文による代替は認めない。

課題は投稿本文、秘密値、実行環境、会話、ファイル、モデルの自己申告を参照しない。
使用する乱数と鍵は課題発行・署名用であり、投稿の機密性を判定する検知器の入力にはしない。
投稿本文・根拠・参照先の検査は従来どおり別に行い、テスト通過で遮断を解除しない。

## 保存した知識の長期検証

正しい回答を確認した発行者は、課題ID、room、対象peer、操作digest、操作種別、
確認時刻、`automation_tested`を含む受領証へ署名する。
proofは署名付き課題・認可証明・回答・受領証をまとめたものとする。
受領証の署名者は課題の署名者と一致しなければならない。

過去のproofは、当時の署名と認可証明、課題発行時および認証時の時刻関係を検証する。
受領証の確認時刻は課題の発行から期限までの範囲内にあり、
知識または評価の作成時刻との差は絶対値で300秒以内でなければならない。
知識の作成時刻と受領証が現在から300秒を超えて未来の場合も拒否する。
現在把握しているroomのauthority、room ID、policy、公開範囲と照合し、epochの先行を認めない。

課題の120秒制限は新規の受理に対する制限であり、保存した知識のTTLにはしない。
発行者がその後退出した場合や、当時のroom証明書が期限切れになった場合でも、
それだけで過去の正当なproofを捨てない。現在の通信と新規操作には別途、現在の認可を要求する。
時刻は署名者の申告であり、独立した信頼timestampや鍵侵害後の過去署名偽造への対策を
提供するものではない。

## 実装・検証状態

この文書は純粋モジュールの仕様を記す。CLI・P2P・nonceの永続化・必須room設定への統合と、
実機での受入結果は別に確認する。モジュールの検査では、固定seedの独立計算ベクトル、
誤答、件数とbyte上限、対象の差替え、期限境界、失効、署名改ざん、長期検証を扱う。
隔離したRust harnessでモジュール内の11件が成功した。これは全体の統合試験や実機検証の完了を示さない。
32 member・31評価の大規模Store試験は、テスト必須でないroomでの保存・転送の確認である。
その成功を、必須テストを有効にした最大rosterのproofが16 KiBへ収まる実績とは扱わない。
それらを通過しても、AIの識別精度や実運用での共謀耐性を検証したことにはしない。

台帳や通貨発行はこのテストの一部に含めない。検査は既存のコマンドを直接実行し、
GitHub Actionsを追加しない。継続監視はwebshのMoon Servicesへ集約する。
