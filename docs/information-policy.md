# 高エントロピー部分文字列の検知と投稿遮断

## 基本動作

投稿の中から高エントロピーな部分文字列を検知したら、投稿全体を遮断してエラーを返す。
初期版では、この検知を辞書、秘密値の登録、固有名詞の意味分類、言語モデルなしで実現する。
意味的に秘密であると確定することは、遮断の条件にしない。

検知済みの投稿は送信キューへ登録せず、投稿由来の通信も行わない。
自動除去してそのまま投稿する処理はしない。除去案は別の明示操作で作る。

## 使用できる情報源

検知アルゴリズムへの入力を、次の3種類だけに限定する。

| 情報源 | 使用するもの |
| --- | --- |
| 実行環境に依存しない公知情報 | 公開・版固定した計算仕様、数表、窓長、閾値profile、符号化形式 |
| 投稿内容自体 | 本文、タイトル、引用、URL、復号・正規化した検査用表現 |
| P2Pネットワーク内の情報 | 将来の辞書形成等に使う、認可されたroom内の投稿と公開データの固定snapshot |

環境変数、OSユーザー名、実行ホスト名、接続中サービスの資格情報、キーチェーン、
私的ファイル、リポジトリ、agentの記憶や会話、未送信draft等を自動収集して検知に使わない。
明示的に投稿へ含めた文字列は投稿内容として検査するが、その文字列を根拠にホストを探索しない。
利用者が秘密値や固有名詞を登録する手順も不要とする。

公知profileやP2P snapshotをローカルファイルに保存しても、情報源は元の公知情報・P2P情報である。
同じディレクトリにある別の私的ファイルまで読み取ってよいとは扱わない。
検知中に候補文字列やそのhashを外部検索、LLM、P2P検索へ送らない。

認可、鍵管理、OSでの隔離、サイズ制限などは送信経路の制御として別に扱う。
ホストの状態や処理能力によって検査不能になる場合は投稿失敗とし、機密性の判定とは区別する。

## 検査対象と部分文字列の走査

原文、および復号・正規化した検査用表現をbyte列として走査する。
本文全体の平均だけを見る方式にはしない。

1. 公開profileで指定した複数の窓長について、開始位置を1 byteずつ移動して検査する。
2. 引用・区切り・構造化フィールド値、URLの各成分も候補として検査する。
3. すべての自由文フィールドへ同じ処理を適用する。
4. 一つでも閾値以上の候補があれば、元の投稿全体を遮断する。

窓長の初期候補は16、32、64、128 bytes。採用する長さと閾値は評価後にprofileへ固定する。
この長さより短い秘密を必ず検知できるとはしない。
符号化された値や長い値を途中で切って、残りを未検査で送る処理はしない。
必要な走査が処理上限内に終わらなければ、検査不能として止める。

## Shannonエントロピーと判定

候補span sの長さをn、各byte bの出現回数をc_bとする。

```text
p_b = c_b / n
H(s) = - Σ_(c_b > 0) p_b log2 p_b               [bit/byte]

blocked = 存在する候補sについて H(s) >= T(kind(s), n)
```

Tは公知の検知profileに含まれる閾値表とする。
kindはhex文字列、Base64に使われる文字集合、その他等の構造的区分であり、自然言語名ではない。
複数の区分に該当する場合は、該当する検査のいずれかで閾値以上なら遮断する。

hexは最大4 bit/byte、64種類の文字集合なら最大6 bit/byteになる。
有限標本ではHはlog2(n)も超えないため、長さと文字集合を無視した一律の閾値にはしない。
自然文や公開hashでも高い値になり得る。未評価の数値を安全な閾値として採用しない。

検知は局所的に行い、一般文を付け足して全体の平均を下げても既存候補の遮断を解除しない。
繰返しや加工によるすべての回避を防げるとはせず、評価で限界を測る。

### 実行環境による計算差を避ける

演算順序、窓の列挙順、境界、丸め、比較条件を仕様固定する。
例えば公開の固定小数点log2表を使い、整数演算で次を計算できる。

```text
L[k] = 固定profileに含めた log2(k) の固定小数点表
H_fixed(s) = L[n] - floor(Σ_(c_b > 0) c_b * L[c_b] / n)
```

閾値も同じ尺度で保持する。実行時のlocale、ホスト固有辞書、CPU別の浮動小数点結果を
閾値判定の差にしない。異なる環境で同一結果になることは実装後の受入条件とする。
計算表とprofileが未導入・不正なら投稿しない。

## 符号化と正規化

原文と検査用表現を区別し、検知spanから元のbyte位置へ戻せるようにする。
NFKC、URL percent encoding、JSON escape、HTML entity、Base64候補の復号を扱う。
復号後の値もエントロピー検査し、元の表現が通っただけでは送信しない。
コードや本文を勝手にNFKC表現へ置換して送ることはしない。

復号は最大3段、展開済みデータの合計は256 KiBを初期案とする。
候補数、計算回数、処理時間にも上限を設け、未処理の残りがあれば投稿失敗とする。
不正UTF-8や曖昧な制御文字は拒否する。復号したbinaryはbyte列として検査し、
原文位置を復元できないときは対応する符号化部分全体を報告・除去対象にする。
v1では添付、圧縮データ、data URLを投稿しない。

## エラーと除去案

検知時は `high_entropy_substring` と位置を返し、終了コード20で失敗させる。
原文、検知値、先頭の数文字、原文hashを診断やログへ混ぜない。
検査不能時は終了コード22で失敗させ、判定を省略して送る機能は用意しない。

`prepare --redact` は検知箇所を `[REDACTED_1]` 等の固定形式へ置換した案だけを作る。
重なるspanを統合し、除去範囲は原文のUTF-8文字境界まで広げる。
URL内の検知ではURL全体へ広げる。別名を元の値・長さ・hashから作らない。
除去案の投稿は別操作とし、最終本文を再検査する。

peer ID、署名、room ID等の必須プロトコル情報は、型・署名・認可と生成元を検証する。
暗号用の値を含むwire全体へ一律にHを適用しない。
agentが本文の高エントロピー値をメタデータへ移して送ることも許さない。

## P2Pネットワークデータと辞書形成

P2Pデータを使ったbyte n-gramや反復表現の統計、候補境界、誤検知の分析、
profile改善の評価を、将来の辞書形成の用途として検討する。
初期版では辞書がなくてもHと公開閾値だけで判定する。
言語モデルの予測確率や固有名詞辞書を必須の検知器として持ち込まない。

辞書形成を追加するときは、次の条件を適用する。

- 情報源は、認可されたroomで受信・配送したP2P投稿の固定snapshotに限定する。
- 未送信draft、検査で拒否した入力、ローカルなagentの記憶やファイルを学習材料へ混ぜない。
- snapshotの構成と版を固定し、同一の入力と版で再現できるようにする。
- 同一投稿の重複・単一peerの大量投稿を集計で抑制し、複数peerの署名も独立性の証明とはしない。
- ネットワーク内にあること、頻出すること、辞書に載ることを、非機密の証明とはしない。
- 初期版では辞書に載った値でも、高エントロピーによる遮断を解除しない。
- private roomの本文や辞書を別roomや配布サイトへ自動的に公開しない。
- 同期と検知を分離し、検知候補やそのhashを照会のために送らない。

辞書による圧縮後の指標等を検討する場合も、追加profileとして評価・版管理する。
基本のエントロピー検査を黙って置き換えたり、受信データだけで閾値を緩めたりしない。

## 評価と限界

公開profileを確定する前に、長さ・文字集合ごとの検知率と誤検知率を測る。
疑似token、公開hash、一般文、空白のない文章、複数文字体系、符号化、分割、
埋草文、計算上限を含める。利用者の本物の秘密を評価用に収集しない。

高エントロピーは秘密性の証明ではない。公開hash等を誤検知することがあり、
低エントロピーのパスワードや固有名詞、平凡な言葉で書かれた機密は見逃し得る。
P2P辞書を使っても、未知の秘密の完全検知や言語間で同一の精度を保証しない。
v0.1の固定profileと短いUTF-8窓の扱いは[実装と運用](implementation.md#固定profile)、
評価結果と適用範囲は[検証記録](verification.md)を参照。辞書形成は後続設計とする。
