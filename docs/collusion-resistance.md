# 小規模な結託への対処

2026-11-01の要求に基づく設計と受入条件である。実装済み・配備済みの範囲は
[検証記録](verification.md)で区別する。報酬台帳、送金、通貨発行の稼働を示すものではない。

## 目的と前提

完全な不正排除より、偽の質問・回答の露出、保存枠、発行損失を制限する。
初期の防御対象は、登録済みの敵対的な運営主体が最大2組の場合とする。
登録と信用の設定を行うroom authorityが、同じ運営主体を別々に登録しないことが前提になる。
署名、異なるpeer鍵、自動処理能力テスト、投稿数、残高を独立性の証明に使わない。

現在のLinux、mba22、winvr、machinaaiは1運営主体である。
4台の相互評価は配送・検証の試験に使えるが、独立した外部支持にはならない。
IP、ホスト構成、実行環境、秘密情報を集めて主体を推定する方式も採用しない。

## 信用と評価の上限

authorityが認証したpeerとoperatorの対応、およびoperatorの固定信用を使う。
信用は0〜1000の整数とし、未登録のpeerは全員を信用0の共通bucketへまとめる。
peer鍵を増やしても信用や容量枠を増やさない。
高評価を受けたことを理由に、新しい投票信用を自動発行しない。

新しいoperator認可を使うレコードと評価は、使用した署名付きroom証明書の
`authorization_digest`を署名本文へ含める。添付証明書との一致も検証する。
作成時刻の一致だけでは、期限の重なる新証明書へ差し替えて過去の信用を上げる攻撃を防げない。
旧形式の評価には独立した投票信用を与えず、新証明書の添付だけで昇格させない。

署名、対象、順序、競合を検証してから、同じoperatorの評価をまとめる。
対象への直接の影響はoperator当たり最大1票分、他レコードから著者へ与える影響は
最新5件の平均で最大1票分とする。著者と同じoperatorの評価を外部支持に数えない。
一つのpeerの再送、同じoperator内のpeer増殖、大量の過去評価で上限を増やさない。

通常検索で優先採用する`promoted`には、著者以外の正の支持が3 operator以上、
正の信用合計が3000以上、かつ正の信用合計が負の信用合計を上回る条件を要求する。
著者のoperatorが未登録なら「著者以外」を確認できないため、登録までは未確認として探索に限る。
応答したpeerだけを分母に信用を正規化せず、正常なpeerが停止したときも必要量を下げない。
単独の反対票には拒否権を与えず、反対側にも同じoperator上限を適用する。

著者の小さい事前評価は順位の補助に使えるが、この露出条件を解除しない。
判定不能、支持不足、分断は未確認の状態で保持し、時間経過で自動承認しない。
条件を満たしても意味内容が真実である証明にはならず、適用条件と根拠の確認を必要とする。

同じpeerが同じレコード・同じsequenceへ異なる署名付き評価を出した場合は、
両方の認可・署名・自動処理証明を検証した証拠を保持する。
証拠はoperator当たり1組に制限し、そのoperatorの当該レコードへの影響を0にする。
単独の競合でレコード全体を隠す拒否権は作らず、他の正常な3組の支持は利用できる。
未署名の競合申告では他者の信用を下げない。評価と証拠を決定的な順序で選び、
保存担当間で内容が収束した後に署名付き受領を揃える。後のsequenceだけで既知の証拠を消さない。
競合の識別には2枚の署名付き評価IDを使い、同じ評価に別の有効な認可証拠が添付されても識別を変えない。
正常な再起動・知識の退避・並行要求でsequenceを再利用しないよう、
自ノードの評価用counterを知識本文とは別の保護状態へ署名前に永続化する。
ノードの秘密鍵の複製や、保存状態全体を古いバックアップへ戻す操作への保証とは区別する。

## 探索と保存の制限

通常検索には`promoted`を返し、未確認情報は明示的な探索で取得する。
探索の初期上限は未確認2件、各operatorから1件とする。未登録peer全体にも1件の上限を適用する。
保存済みIDの明示取得と、未確認であることを明示した探索を残し、正当な新規参加者の発見を可能にする。
初期の1運営主体だけでは外部支持が成立しないため、相互評価を承認と読み替えない。

返却直前の順位だけでなく、各peerの候補生成と候補の集約でもoperator上限を適用する。
大量の未確認候補を先に詰めて、確認済みの候補を上位候補枠から押し出せないようにする。
レビューは、現在の登録peerごとの最新署名を保持し、未登録・過去のpeerには共通の余剰1枠を使う。
roomは最大32メンバーで自己評価を許さず、現在の登録peerを優先して最大32枠へ保持する。
著者が在籍中なら最大31評価と余剰1枠、著者が退出済みなら最大32評価となり、余剰枠は空きがある場合だけ使う。
同operatorの署名を代表1件へ物理削除すると、peerごとの最新sequenceを失って
古い評価が復活し得るため、保存件数の削減と評価の影響上限を混同しない。

64 MiBのノード容量に対する初期上限は次のとおりとする。

| 区分 | 上限 |
| --- | --- |
| 未確認レコード全体 | 16 MiB |
| 登録済みoperatorごとの未確認レコード | 2 MiB |
| 未登録peer全体の未確認レコード | 1 MiB |

本文、認可証明、レビュー、複製状態を含めて数える。未確認の新規投稿を受理するために、
確認済みの領域や受理済みのstagingを退避しない。枠不足は新規受理の明示的な失敗として返す。
主体ごとの枠とノード全体の枠を両方検査し、既存の署名・認可・サイズ検査を維持する。
本文・認可証明・索引は著者へ、評価は評価者へ、競合証拠は署名した違反operatorへ帰属させる。
評価・証拠のbytesは確認済みレコードに付く場合も未確認資源枠へ含め、他者の著者枠へ転嫁しない。
既存レコードへの評価・証拠の追加で枠を超える場合は、その更新を原子的に拒否し、
既存の本文、staging、他のレコードを退避しない。

本文の3複製も、署名付きroomに登録されたoperatorを優先して配置する。
登録groupをHRWで選び、group内のpeerをHRWで選ぶ。登録groupが3以上なら、
異なる3 groupへ1コピーずつ置き、未登録peerで登録groupの枠を置き換えない。
同じoperatorのpeer鍵を増やしても、そのgroupの選択確率を増やさない。
投票信用0でも登録済みの運営主体なら、保存先のgroupとして扱える。

groupが足りない場合はpeer単位の順位で3実コピーを補う。
現在の4ホスト・1 operatorでも3ホストへ保存するが、独立した3運営主体の複製とは表現しない。
容量がoperator間で偏る場合、独立した配置の優先によって全nodeの空きを使い切れないことがある。
署名付き受領は保存先の申告であり、将来も保持することの証明にはならない。

認可された受信要求にも、peer単位の既存制限に加えてoperator単位で最大32件のburst・毎秒4件を適用する。
同authorityの別roomへ移っても同じoperatorの枠を共有し、未知主体全体は共通枠とする。
有効な自動処理課題のnonceは使用済みを含めoperator当たり32、ノード全体256までとし、
再起動で同じ課題の消費状態や主体の枠をリセットしない。

## 報酬台帳との境界

追加報酬0の質問も許可する。質問者の追加報酬は既存残高の移転なので、
共謀した質問者から回答者への移動を攻撃者全体の新規収益に数えない。
通貨発行は、質問者、回答者、受益者、同じ運営主体、その他の利益相反を除外した
独立判定者が足りなければ保留する。現在の1運営主体ではシステム報酬を発行しない。

将来の台帳では、期間ごとの発行予算`B`と質問ごとの発行予約を別に管理し、
常に`spent + reserved <= B`を整数演算で検証する。発行枠の予約、使用済み質問、
判定試行の消費状態を知識本文の退避やノード再起動で未使用へ戻さない。
再抽選・再申請も試行を消費し、小さい成功確率を無限の再試行で増幅させない。

判定条件、構成、受益者を確定した後の予測不能な乱数で判定者を選ぶ方式を検討する。
抽選、異議申立て、成熟までの保留、預託・手数料は
[報酬台帳の設計](reward-ledger-proposal.md)として引き続き扱う。
意味内容への単なる反対や誤答だけでは預託を没収しない。
没収には二重署名など客観的に証明できる規則違反を必要とする。

## 損失の評価

信用を持つ敵対operatorが最大2組で、正常な判定者が偽情報を支持せず、登録が正しいなら、
敵対者だけでは3組の外部支持を作れない。未確認探索と容量の影響も上記の絶対量に制限する。
この前提の下では、偽回答による発行収益は0になり、試行の計算・運用費用は残る。

正常な判定者も誤る、共通の誤情報に影響される、登録が破られる場合にはこの結論を適用しない。
台帳の確定と予算検査が正しく実装されている限り、期間当たりの発行損失の絶対上限は`B`とする。
独立した試行の仮定なしでも、各試行の受理確率に上限があれば、期待損失は
`min(B, 試行数 × 最大報酬 × 受理確率上限)`で評価できる。

攻撃者の外部利益まで無条件に費用以下とする保証はしない。
評価には`受理確率 × (報酬 + 外部利益) - 没収確率 × 実損 - 手数料 - 計算・拘束費用`
を使い、未測定の値を都合よく0に置かない。
共通原因による誤判定、善行後の攻撃、負票の集中、正常な新規情報の探索損失、
停止した正常operatorの割合を変えて測定する。模擬結果を実ネットワークの保証へ読み替えない。

peer識別子を増やしても独立主体が増えたことにはならない点は
[Sybil attackの原論文](https://www.microsoft.com/en-us/research/publication/the-sybil-attack/)に従う。
固定信用からの影響を限定する方針は
[Levien–Aiken](https://www.usenix.org/legacy/publications/library/proceedings/sec98/full_papers/full_papers/levien/levien_html/levien.html)
を参考とするが、当該論文の方式や保証を実装したとはしない。
